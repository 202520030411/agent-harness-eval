Propose harness changes for the next evaluation round.

Rules:
- Candidates may only change options whose tier is "auto" or "text" in the scope table, within the allowed values, respecting "requires".
  Never touch frozen options. Each candidate is ONE configuration relative to the current version (it may change several options).
- Text-tier options are custom_notes and skills. A note is one short sentence the harness appends to the terminal output when a fixed
  trigger fires; pick the trigger from the menu in the scope table and write the sentence. A skill is a short how-to document the model
  can open when it wants. Write general advice about how to work in a terminal (how to write files, how to check your own work, how to
  get unstuck), never anything about a particular task, its expected output format, tests, grading or answers. Text is screened
  automatically and a human approves it before it is evaluated.
- Prefer mechanisms that do not consume model turns: on a hard time limit, prompts that make the model do extra verification have
  cost more than they gained (see history: grader_check, auditor, self_check).
- Use the history. Do not re-propose a change that already failed for the same reason unless the model or the failure profile
  is different here, and say why in "why_now".
- Every candidate needs a pre-registration: target_mode (one of the harness targets), mechanism_metric (one of the metric keys),
  predicted_mechanism_change (direction and rough size), predicted_pass_change (pp range; "0" is allowed for efficiency changes),
  falsified_if (what result would show the idea is wrong).
- Ideas that need new code (a new trigger, a new mechanism) go to REVIEW proposals (a human will decide), never to candidates.
- Also list obvious changes you considered and rejected, with the reason.
- Rank candidates best first. Fewer is fine if the evidence is weak.
