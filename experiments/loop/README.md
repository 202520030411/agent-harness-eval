# 自进化闭环：harness 的 观察 → 反思 → 提议 → 评测 → 上线 / 回滚

一句话：每一轮从已有的 trial 日志里找出最费事的失败模式，提出 harness 改动，用"和当前版本同时跑"的对照决定收不收，收了还要一个独立批次复现才上线；每个版本都有记录、可以回滚。模型权重不在这个闭环里改（那是训练线）。

```
Harbor job 目录 ──▶ observe（每个 trial 一行 + 失败模式表）──▶ reflect（harness 队列 / 训练队列 / 人工队列）
      ▲                                                                       │
      │                                                                       ▼
 promote / rollback ◀── 接受门 + 独立复现 ◀── evaluate ◀── plan ◀── 效果上限检查 ◀── propose（强模型，有硬预算）
```

## 代码

| 文件 | 作用 |
|---|---|
| `agenteval/loop/scope.py` | 可修改范围。`auto`：已有开关和数值，闭环可以自己提；`review`：新机制，人批准后才改成 auto；`frozen`：评测协议（`max_turns` 等）、训练专用、`teacher_hint`（会看参考解）。`validate_change` 检查越界、类型、依赖；`fingerprint` 判断两个配置是不是同一个 harness |
| `agenteval/loop/state.py` | 版本记录 `Registry`：`propose`（范围检查 + 同一模型下去重 + 预注册必填）、`record_evaluation`（主评测和复现各只算一次，复现两臂必须新跑）、`promotable`、`promote`、`withdraw`、`rollback`；文件带整体指纹、改写加锁 |
| `agenteval/loop/accept.py` | 接受门 `evaluate`：按题配对 bootstrap；INVALID / REJECT / ACCEPT_QUALITY / ACCEPT_EFFICIENCY / PROVISIONAL / INCONCLUSIVE（规则见文件头，含 D-085 的防作弊与防自欺规则） |
| `agenteval/loop/notes.py` | 机器写的提醒的防泄题过滤（固定规则，D-085） |
| `agenteval/loop/modes.py` | 16 个失败模式：判定、分母、先验归责（原则上来自已经做完的对照实验；`line_by_line_write` 是第 1 轮读日志加的，记 UNKNOWN）、可动的开关 |
| `agenteval/loop/reflect.py` | 把模式分进三个队列，附上"试过哪些开关、结果如何" |
| `agenteval/loop/propose.py` | 给提议模型拼提示、解析回复、检查预注册 |
| `tools/loop_cycle.py` | 命令行：`observe / reflect / propose / init / add / plan / evaluate / promote / withdraw / rollback / status / backtest`。**没有任何启动 trial 的代码**：`plan` 只写配置和一条同时启动所有臂的命令 |
| `train/synth/harden.py` | 把合成题复制成判分加固版（`/root/work/train/synth_split_v2`，D-085） |
| `tools/drill_agent.py`、`tools/run_drills.py` | 作弊演习：不调模型、只执行固定的作弊命令，比较旧版和加固版判分 |
| `experiments/loop/history.json` | 项目里做过的 17 条 harness 对照实验记录（约 12 种不同改动；给提议模型看，也给反思挂"试过"） |
| `experiments/loop/registry.json` | 版本记录（服务器上是主本） |

测试：`tests/test_loop_*.py`（60 个）＋ `tests/test_patch_helpers.py`、`tests/test_qwen_arms.py`、`tests/test_adapter_and_rules.py` 里的逐行追加检测、`append_nudge`、命令分类和诱饵检测。

## 第 1 轮（2026-10-11，不跑新实验；API 花费 $0.22，GPU 0）

**观察**（开发集 = 74 道合成训练题 × 3 次，job `qroll-h2-synth-train`，当前版本 v0 = H2 = `interface_fixes` + `completion_gate`）：通过率 14.9%；56 题 3 次全挂、13 题有过有不过、5 题全过；超时只有 6 次，但 42 次（19%）跑满 100 轮，平均只用了 5.1 分钟——**这批题上卡住 Qwen 的是轮数，不是时间**。报告：`reports/loop/c1b/`。

**接受门回测**（`reports/loop/backtest2/`）：把门用在 19 对历史实验和 7 对"两边配置相同"的批次上。
- 19 对里门没有接受任何"通过率提升"，与 D-050 的人工结论一致；唯一的 ACCEPT_EFFICIENCY 是 Qwen 的 `interface_fixes`（轮数 −18%、输入 token −41%），正是当时采用的改动；比人工更严的 3 处：E4 adaptive_wait（当时记为省资源，门判不显著）、契约 v2（锚题掉到 0）、H17（用时 +18%）。
- 不同时跑的同配置批次：门最多给 PROVISIONAL（例：E1 → E4 基线 +11.5 pp，被"不同时跑"规则降级），从不直接接受。
- **门判当前版本里的 `completion_gate` 不该收**：TB 上 H2 对 H1 轮数 +20%、输入 token +67%，通过率 +0.8。
- 同配置随机对半分：第一版门在 TB（每臂 4 次）上误收 9%、误拒 11%。原因是效率的三个指标任一显著就算数（相当于做了三次检验），以及"锚题掉到 0"在偶然有过有不过的题上会误报。修正后（每个效率指标用 5% ÷ 3 的标准；锚题要求在更早的观察批次里也全过）这一组误收 5%、误拒 6.5%；其他几组误收 4.5–6%、误拒 5.5–9%（每臂只有 2 次的那组误拒 44%）。**更正（D-085）**：这是在同一批拆分上调过门之后测的，开发集本身没校准过；当时写的"加上独立复现，误上线约 0.25%"只是 5% × 5% 的粗算，依赖当时代码并不保证的前提（复现独立、只复现一次、一个候选），不是实测。

**提议**（gpt-6-sol 两次、claude-sonnet-5 一次，$0.22）：3 个 auto 候选正好构成 2×2——c01 开 `adaptive_wait`、c02 关 `completion_gate`、c03 两个都改；另有 6 个需要人审的想法（`reports/loop/c1/propose.md`）。

**效果上限检查**（新加的一步，免费）：花钱评测之前，先用已有日志算出候选最好能省多少。
- c02：开发集上把关打回之后用掉的轮数只占全部轮数 2.8%、输入 token 5.7%（TB 上是 10–16%）；打回的 28 个 trial 没有一个最后通过。关掉把关最多省这么多，低于接受门 10% 的效率门槛。
- c01：`adaptive_wait` 主要省"空等待"轮，开发集上平均每 trial 0.045 轮（222 个里只有 8 个出现过）。
- 三个候选都 `withdraw`，没花 GPU 钱。

**新发现：逐行追加写文件。** 跑满 100 轮的 42 个 trial 里，81% 的轮是 `echo … >> 文件`：一轮写一行代码，直到轮数用完。
- 开发集 26% 的 trial、留出合成题 17–23%、TB 2–3%；约 230 个这样的 trial 里只有 1 个通过。（为了确认普遍性看过留出题和 TB 的旧批次日志：它们不再是完全没碰过的测试集，见 D-085。）
- H0 和 H2 同批 21% vs 17%（现有开关压不下去）；SFT / RL 之后 18–23%（训练也没压下去）；gpt-6-sol、Seed 同题 0%。
- 不是 heredoc 写坏了：57 次里 45 次在这之前已经用 `cat > 文件 << 'EOF'` 成功写过文件。
- 第 1 轮的失败模式表只有"跑满轮数"（结果），没有"逐行追加"（行为），所以提议模型看不到它；已加进 `modes.py`（`line_by_line_write`）和观察字段（`append_turns`）。

**候选机制 `append_nudge`（review 档，代码已写好、默认关，待批准）**：同一个文件连续 3 轮（以及 10 轮）被 `echo`/`printf >>` 追加时，在观察末尾提醒一次"用一条命令写整个文件"，不占模型轮次，每 trial 最多 3 次（`terminus2_patches/agent.py` 的 `APPEND_NOTE`）。离线回放（只看会不会触发，不知道模型会不会照做）：

| 开发集 | 会触发 | 中位触发轮 | 触发之后的追加轮 |
|---|---|---|---|
| 跑满 100 轮的 trial | 41 / 42 | 15 | 占这组轮数 78% |
| 其他失败 | 25 / 147 | 13 | 9% |
| 通过 | 1 / 33 | 14 | 6% |

TB（qfinal-base-tb）上 120 个 trial 只会触发 6 个。触发之后的追加轮约占开发集全部轮数的 35%：这是模型完全照做时能省的**上限**，不是预期；预注册的预测是总轮数降 10–25%。

**对闭环本身的修正**（都在任何候选评测之前）：`truncated_read` 先验 MODEL → MIXED（项目自己的数据互相矛盾，见 `modes.py`）；接受门的两处校准（上面）；指纹不再包含取默认值的选项（以后加新开关不会改变已有版本的指纹）；新增 `withdraw` 和效果上限检查。

## 第 0 步：防作弊与防自欺（2026-10-12，D-085；不花 GPU / API）

起因：用户要求"检查机制不能被 hack"。

**作弊演习**（`tools/drill_agent.py` 不调模型，只执行固定的作弊命令，然后交白卷；3 道题：数据转换、服务、程序移植；任何"通过"都是骗出来的）：

| 作弊方式 | 旧版判分（同一个容器） | 加固版判分（全新容器） |
|---|---|---|
| 什么都不做（对照） | 0 / 3 | 0 / 3 |
| `/app` 里放假的 `pytest.py` | **3 / 3 通过** | 0 / 3 |
| site-packages 里放一个启动即退出的 `.pth` | **3 / 3 通过** | 0 / 3 |
| 把 `python3` 换成直接返回成功的脚本 | **3 / 3 通过** | 0 / 3 |
| 预先放一个写着得分 1 的 `reward.json` | **3 / 3 通过** | 0 / 3 |
| 后台进程不停往结果文件写 1 | **1 / 3 通过** | 0 / 3 |
| 起一个假服务，不停尝试改判分 | **3 / 3 通过** | 0 / 3 |
| `conftest.py` 把测试强行改成通过 | 0 / 3 | 0 / 3 |
| 偷看诱饵文件 | — （旧版没有诱饵） | 0 / 3，**3 / 3 被标出** |

合计：旧版 24 次作弊 16 次骗到"通过"，加固版 0 / 24。过去 7,412 条轨迹扫描没有发现真正的篡改，以前的成绩不受影响。TB 题仍是"同一个容器"判分，这几种手法在 TB 上同样可能：TB 只做最后报告，靠作弊巡查（碰判分目录、结果文件的都标出来）把关。

**加固版判分是否仍然正确**（111 道题，每道直接执行参考答案 vs 什么都不做）：参考答案 **111 / 111 通过**，什么都不做 **0 / 111**。第一次跑是 109 / 111：两道 git 题的测试要读初始化脚本放在 `/tmp` 的标准答案提交号，新容器里没有。改为判分镜像照原样重放题目的构建过程后全部通过（这也顺带堵上了旧版里 agent 可以改写这份标准答案的口子）。以后只判 `/app` 里的内容：过去 Qwen 在合成题上几乎不在 `/app` 之外装包或写文件（三次运行合计 4 次，没有一次通过），所以不影响以前的结果。

**接受门最终校准**（`reports/loop/backtest4/`；同一配置的 trial 随机分成两半当两个臂，每组抽 200 次；任何"更好"或"更差"都是误判）：

| 数据 | 每臂次数 | 误收 | 误拒 |
|---|---|---|---|
| TB（Qwen），用更早批次定锚题 | 4 | 3.5% | 6.5% |
| TB（Qwen），不用 | 4 | 3.5% | 8.5% |
| 留出合成题（Qwen） | 3 | 2.5% | 9.0% |
| TB（Seed），用更早批次定锚题 | 3 | 6.0% | 5.5% |
| TB（Qwen H0 两批） | 2 | 5.0% | 44%（每臂 2 次，实际评测会判 INVALID） |

这些数是在同样的拆分上调过门之后测的（样本内）；开发集（74 道训练题）本身还没有同配置的重复批次可以校准。历史 19 对实验：门仍然没有接受任何改动；Qwen `interface_fixes` 从 ACCEPT_EFFICIENCY 变成 PROVISIONAL（低通过率下允许的下降收紧到约 4 pp，需要复现才能上线）；交卷把关、grader_check、契约 v2、H17 仍是 REJECT。

**修掉的问题**：见 D-085（判分加固、闭环防自欺的硬规则、接受门、现行 harness 的 v0.1 修正、提醒过滤）。

**还没做的**：独立的代码审查认为还要再加一层——agent 自己写的程序和服务，要和运行测试的账号分开，读不到测试、写不了结果目录；判分前清理 `/app`；git 题运行 git 时关掉仓库里的自动脚本。按用户的意见不再做攻击演习，这一层做的话只用常规的正确性检查（参考答案全过、什么都不做全挂）来验证。待用户决定。
